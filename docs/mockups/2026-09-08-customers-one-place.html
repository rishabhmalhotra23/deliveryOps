Customers, in one place

Mockup for approval, 2026-09-08. Every name, category and count below is live production data (41 customers, 17 active, 24 retired, 1 soft-deleted).

Why

What's broken today

  • active does almost nothing. It is honoured in exactly two places, both in lib/processes/loader.ts (lines 293 and 444) — the customerOptions list feeding Delivery's process picker. So retiring a customer stops you assigning new processes to it, and has no other effect anywhere.
  • /customers ignores it completely. listCustomers() has no active filter and CustomerRow doesn't carry the field. 24 of 41 customers are retired and the list shows all 41 identically, including 13 marked Churned.
  • Two editors, one row. Delivery → Configure → Customers edits name, category, active, AE, partner, Slack and SF ID — a strict subset of the /customers/[key] record card, through a different route with a different allow-list. (I widened Configure on 2026-09-08 to close a gap, which deepened the duplication instead of resolving it.)
  • Two axes disagree. The zone chips derive "Closed — no longer active" from custom_category, while active is its own column. They agree on 35 of 41 rows and contradict each other on 6. Section 4 surfaces those rather than picking a winner silently.

6

Under the hood

  • listCustomers() keeps returning every non-deleted row; the list page threads active onto CustomerRow and hides retired client-side, so the counts, search and zone chips all stay computed from one array.
  • PATCH /api/customers/roster and its route are deleted. The row menu uses the record card's existing POST /api/customers/[key]/manual-update, so there is one allow-list, one provenance write and one audit event (CATEGORY_CHANGED / PROFILE_UPDATED) instead of two that drift.
  • countCustomerProcesses() moves from serving the Configure tab to serving the list — same query, and its comment gets corrected.
  • customers.active stays the single truth for "still a customer". custom_category stays a reporting bucket, as lib/supabase/types.ts already documents — the zone chips keep deriving from it, but they no longer claim to answer a question active owns.
  • A test pins that a retired customer is excluded from the default list and included with the toggle, and that its 360 page and search still resolve — the guardrail against "hidden" quietly becoming "gone".

Categories become configurable — label, colour, and zone

Because minting one from the picker today only gets you the label. Everything else about a new category is hardcoded.

What happens today if you add "To be dropped post contract expiry" from the record card: the name saves fine (custom_category is free text), but zoneForCategory() has no entry for it and falls through to ?? "Focus" — so a customer you are winding down files under Focus, the active book, and its chip renders untoned because CATEGORY_VARIANT has no entry either. The label is configurable; its meaning is not.

+ Add a category

Zone is the field that matters. It is the one thing a minted category cannot currently express, and the one with real consequences — it decides which group a customer appears under on this page and whether it reads as part of the active book. Picking Closed here is what makes "to be dropped post contract expiry" behave like a wind-down instead of quietly joining Focus.

No migration risk, unlike the process vocabularies. customers.custom_category is plain text (0005) — no enum, no CHECK. So adding a category is an ordinary INSERT, not the irreversible ALTER TYPE … ADD VALUE that add_vocabulary_value() has to run for the process enums. A customer category can therefore be genuinely deleted, not just retired.

Under the hood

  • A new vocabulary = 'customer_category' in vocabulary_values (0042's table), seeded from today's CUSTOMER_CATEGORIES, CATEGORY_TO_ZONE and CATEGORY_VARIANT so nothing changes appearance on day one.
  • One new nullable column, rollup, holding the zone. Only customer_category uses it; the process vocabularies leave it null.
  • zoneForCategory() and the chip tone read the DB first and fall back to the compiled maps — the same "DB wins, hardcoded default behind it" shape resolveHue() already uses, so a missing row degrades to today's behaviour rather than to nothing.
  • add_vocabulary_value() is not touched: it exists to run ALTER TYPE for real enums, and this isn't one. Customer categories go through a plain insert, which is why they can also be deleted.
  • A test pins that every seeded category resolves to the same zone and tone it resolves to today, and that an unknown category still lands somewhere legible rather than untoned in Focus.
