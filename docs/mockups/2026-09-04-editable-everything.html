Everything editable — and corrections that stick

Mockup for approval · 2026-09-04 · no code changed yet

1Where we are

The Customer 360 has no editing at all

There is not a single manual-update or updateProfile call anywhere under app/(app)/customers/[key]/. ARR, renewal, industry, tier, contacts and headquarters are display-only. The only inline editing in the whole app is on the Dashboard → Trends workload drilldown.

And correcting a Salesforce-derived number today means editing TypeScript and deploying — CONFIRMED_ARR_OVERRIDES in lib/commercials/confirmed-arr.ts is a hardcoded map. It currently holds exactly one entry, Norco, with a source comment explaining that Salesforce says $689K and GTM says $311K. That is the thing you are describing, and it is the design to replace.

The chip is a link to this. Nothing is hidden: the sync value is still visible, so a wrong correction is findable rather than silently permanent.

This is exactly the flow you described — ask whether the current value was incorrect, and remember the one you gave. The one-off option matters: sometimes the sync is right and the data is just late, and forcing every edit to become permanent would quietly freeze fields that should keep tracking Salesforce.

4How it's stored

Field kindWhere the value livesHow an edit is kept
DeliveryOps-owned
category, AE, partner, active, notes		 customers / processes column Write the column. Already works; deliveryops_protected_fields shields it from sync.
Profile
industry, tier, HQ, contacts, objectives		 profiles column Write the column via updateProfile, which already stamps field_provenance. No sync writes this table, so no conflict — it just has no UI yet.
Salesforce-derived
confirmed ARR, renewal date, employees		 Nowhere. Computed at read time from sf_* New field_overrides row. This is the only genuinely new mechanism.

The third row is the whole reason a new table is needed. The Salesforce sync writes only to sf_accounts / sf_opportunities / sf_cases — it never touches customers or profiles. So a derived value has no column to edit, and "make it editable" means storing an override that wins over the derivation. One table, keyed (entity_type, entity_id, field), holding the value, who set it, when, and why — which is CONFIRMED_ARR_OVERRIDES promoted out of source code and given provenance.

5Scope

In this change

field_overrides + resolver, replacing the hardcoded ARR map (Norco's entry migrated across with its existing comment as the reason). The confirm dialog. The override chip and its provenance card. Customer 360 hero + stats rail + profile fields become editable. manual-update's allow-list widened to every DeliveryOps-owned column on customers.

Not in this change

Writing back to Salesforce — an override is local truth, not a push. Editing the sf_* cache directly, which the next sync would flatten. Bulk override editing. And nothing about the events pipe, which is a separate problem (see below).
