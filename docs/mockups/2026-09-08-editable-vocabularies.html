Adding a value can’t be undone — Postgres has no way to remove an enum value once it exists. To take one out of circulation, untick Offered in pickers instead: rows already using it keep rendering.
Label, short label, colour and order are yours to change any time. The value itself (to_be_retired) is fixed once created, because rows point at it.

2Colours stop being per-browser

Configure → Colours wrote into localStorage (dops.viewPrefs), so it was per browser: two people looking at the same board saw different colours, and a new laptop started from defaults. Colour is a property of the value, not of the viewer — so it moved into vocabulary_values.hue alongside the label, and the Colours tab now edits the same rows this tab does. One place, shared by everyone.

The 8-hue palette is unchanged, and the per-value defaults seeded from today's hues.ts maps, so nothing looks different on the first load after deploy.

3What stays in code, and why

The enum types stay. I looked at converting the columns to plain text and decided against it: 17 exhaustive Record<MigrationStage, …> maps depend on those unions, and that is the safety net which forced to_be_retired to be given a label, a short label and a colour — the build would have failed if any had been missed. Converting would trade “adding a value needs a migration” for “adding a value silently renders a blank grey chip,” which is a worse deal.

So a value added in the product is known to the database and to every picker immediately, and gets its label and colour from the table. What it does not get is a place in the routing rules — a brand-new migration stage lands in V2 migration, because sectionFor() sends everything that isn't v2_native there. That is the correct default, and changing it is still a code decision.
